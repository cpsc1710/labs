CPSC 1710 · Lab 8 · 75-minute plan

Run a business for 30 days

On Tuesday you played a thermostat with a delay in it, and placed fixes on Meadows' ladder. Today you watch an agent run a system with delays in it: a small vending business, for 30 simulated days. The benchmark is Prosus Vending Bench: six machines at three locations in Amsterdam, €1,500 to start, 22 tools, and a score equal to the money in the bank at the end.

You will start an agent on the business, play the same business yourself for three days while it runs, and then read what it did. By the end, you should be able to find a mistake that the agent's final score hides, and name where in the system a fix for it would land.

Work with a partner, but use your own course key. Open the Lab 8 notebook in Colab (or download it). Your key should already be saved as the Colab secret OPENROUTER_API_KEY, from Labs 4 and 7. One agent run with the default model takes 2–5 minutes and costs about two cents; every run is capped at $0.50.

0. Setup

Run the two setup cells. The first downloads the benchmark and installs two libraries (about a minute). If it stops with a key error, check the secret's name and that Notebook access is on. The rules for the key haven't changed: never paste it into a cell, a prompt, a screenshot or a shared document.

1. Start the agent

The agent gets a briefing and 22 tools. As in Lab 7, a program around the model (the harness) sends it the conversation so far, runs the tools it asks for, adds the results, and sends everything back. That repeats until day 30 ends, the budget runs out, or the agent stops asking for tools. The run happens in the background, so you can carry on with the notebook. Run agent_status(RUN) whenever you want to check on it.

Everyone uses seed 1, so all of us, and the agents, are running the same world. Do not restart the Colab runtime while your agent is running: that stops it.

2. What the agent is told

The notebook prints the agent's whole briefing and its tool list. That is everything it knows at the start. Read the briefing and answer Checkpoint 1:

  • What does every action cost, besides money?
  • When do sales happen? When do orders arrive?
  • What counts as the score? What doesn't count, even though it's worth something?
  • What would you want to know on day 1 that the briefing doesn't tell you?

3. Play days 1–3 yourself

Run start_my_game() to get your own copy of the same business. You use the same tools through play(...), for example:

play("search_web", query="snack wholesaler Amsterdam", why="find suppliers")
play("check_offers", supplier_id="zuidas-groothandel", quantity=40, why="compare prices")
play("wait_for_next_day", why="nothing left worth the time today")

Your goal: leave the business on day 4 in a better position than the agent will. Rules:

  • Use only the business tools. Don't read the simulator's code or settings. The agent can't, and the point is to play under the same conditions.
  • Give every call a why="...", with your real reason in a few words. Your reasons are the most useful thing you'll write today.
  • Watch the stamp at the end of each result, such as [Day 1/30 — Mon 05 Jan 2026 09:30 — balance €1,500.00]. Every call moves the clock.
  • One partner types and one keeps notes, and you swap at day 2. Before each wait_for_next_day, the note-keeper writes one line: what we did today, and what we expect tomorrow.

For Checkpoint 2, record two decisions you would defend (with the evidence you had at the time), one you regret, and one thing you found out that the briefing didn't tell you. my_days() lists your calls and reasons so far.

4. Read the agent's first three days

agent_days(RUN, 1, 3) prints every tool call the agent made on days 1–3, with the time and the bank balance after each one. agent_tools(RUN) counts its calls by tool and lists the tools it never used. Compare them with your own three days:

  • What did the agent do that you also did? What did you do that it didn't?
  • Which tools did it never use? Did you use any of them? Could any of them have earned money?
  • Did it spend time on anything you wouldn't have?

5. Read the end of the run

agent_end(RUN) shows the agent's last few turns and what the benchmark recorded. Look at model_result_subtype (how the run ended) and completed. A run that stops before day 30 ends scores €0, whatever is in the bank. Check one thing the agent said about its own results against the recorded numbers.

6. Class board: is one run enough?

Add your agent's model, final bank balance and outcome to the class board. Reference runs on the same world (seed 1, 30 days):

The Sonnet runs used a different harness (Claude's command-line agent), so compare them with each other, not with today's runs. If two runs of the same model on the same world can differ by €626, how many runs would you want before saying one model is better than another?

7. Diagnose: one failure, one fix, one level

Pick one failure from the agent's run or from your own play: something that cost money, time or sales.

  1. Place it on the ladder. Which part of the system made it happen?
  2. Propose one fix and name its level. Does it change the harness around the model (what the agent sees, remembers, or is allowed to do), or the model itself? If you'd swap in a bigger model, say which level you expect the new model's behaviour to change. A swap has no rung of its own.
  3. Does your fix strengthen the agent's own loop, or shift the work onto a human?

Write your failure, fix and level on the board. The ladder from Tuesday, for an agent:

12Numberstemperature, max tokens, prompt wording, how many turns it gets
11Bufferscontext window, cash reserve, inventory on hand
10Stocks and flowsmemory: what piles up (notes) and what drains away (old turns)
9Delaysdeliveries that arrive days later; feedback many steps after the action
8Balancing loopschecking the work: inventory counts, sales reports, a human approving
7Reinforcing loopsthe agent building on its own mistakes
6Information flowswhat the harness shows the agent: pending orders, logs, its own history
5Rulespermissions, spending limits, what gets rewarded
4Self-organizationthe agent writes its own tools or changes its own harness
3Goals"maximize the bank balance" vs "keep the machines stocked"
2Paradigm"helpful assistant" vs "shopkeeper"
1Transcending paradigmsholding any of these lightly

Optional: try your fix

At the end of the notebook, start_agent takes extra_instructions="..." (text added to the end of the agent's briefing) and context_chars=... (how much of the conversation the agent sees on each turn). Run your fix and a plain run side by side. One run of each isn't evidence of anything (Step 6), but it's a start, and it's the setup for the homework.

Before you leave

Run the last cell, then download lab8-evidence.zip from the Files panel. It holds your trace and your agent's run folders, and Colab deletes them when the session ends. Keep one moment where the agent did something sensible and one where it went wrong.

After lab: read an expert's run

The journal of Claude Opus 5.5 playing the same benchmark (seed 4, 30 days): it wrote down a reason for every decision and ended at €4,200, against the scripted bot's €3,274. Read it after you have played, not before. The journal is honest that it isn't a clean run: before starting, the player had already seen six other runs, and once you've read it, so have you.

If something goes wrong

  • Key error in setup: the secret must be named exactly OPENROUTER_API_KEY, with Notebook access on.
  • agent_status says "not started, or failed": open runs/<name>.log in the Files panel and show your TF.
  • "Your game is not running": run start_my_game(). This starts again from day 1.
  • The runtime disconnected: rerun the setup cells. Your agent run has stopped, so start a new one.
  • A tool says an argument is wrong: run play("get_status") to check the clock, then fix the argument. Bad calls cost game time too.
